Executive Summary

A mid-size Canadian retailer, Maple & Pine, runs 4 regional stores plus an online channel. Sales are healthy — but teams work in silos: analysts build reports, ops chase stock-outs by hand, and leaders wait days for answers. This demo shows how Microsoft Fabric IQ unifies that into a single, governed, AI-ready foundation on one copy of the data.

Value highlights

  • One source of truth — Lakehouse + Direct Lake means reports read live Delta tables with no import/refresh lag.
  • A shared business language — the Ontology binds Store/Product/Customer/Order/Inventory to real tables, so humans and AI agents reason on the same definitions.
  • Self-service answers — business users ask questions in plain English via the Data Agent instead of queuing report requests.
  • Insight → action — the Activator turns a low-stock signal into an alert in someone's inbox automatically.
  • Governed & trusted — measures, relationships and security live once in the model, reused everywhere.
  • Fast to stand up — the entire demo deploys code-first via the Fabric REST API in minutes, repeatable across tenants.
Who this is for: account teams and partners running a Fabric IQ retail demo, and customer architects who want a repeatable, end-to-end reference they can deploy in their own environment.

Demo Storyline — "Maple & Pine"

A 4-act narrative that walks from "what happened" all the way to "act automatically", showing every Fabric IQ capability on one connected dataset.

Setup: Maple & Pine runs stores in Ontario, Québec, BC & Alberta plus an online channel. Revenue is healthy (~$106K, 350 orders) but the ops team keeps getting surprised by stock-outs. Leadership wants one connected view — and wants to ask questions in plain English.
Act 1 · Power BI Report

"What happened?" — the executive pulse

  • Open RetailDemoReport → Sales overview: Total Sales, Avg Order Value, Units Sold, Online vs In-Store split.
  • Store performance: rank provinces; see who pulls their weight.
  • Top products: the hero SKUs driving the category mix.
  • Hook: it's Direct Lake — no import, no refresh lag; it reads the lakehouse live.
Act 2 · Fabric IQ Ontology

"How is it all connected?" — the business model

  • Open RetailOntology and show the graph: Customer → places → Order → contains → Product → has → Inventory; Order → at → Store.
  • Each entity is data-bound to a real lakehouse table — a living model, not a diagram.
  • Message: this is the shared language humans and AI agents both use.
Act 3 · Data Agent

"Just ask." — conversational analytics

  • Ask live: "Which store has the highest revenue?"
  • "What are the top-selling products?" · "Which products are low in inventory right now?"
  • "What's the average order value for Online vs In-Store?"
  • It answers using the same governed measures + ontology behind the report — no SQL, no tickets.
Act 4 · Operations Agent + Activator

"Don't make me watch dashboards." — proactive action

  • Show the InventoryEvents stream in RetailEventhouse (low-stock + demand-spike events).
  • The Operations Agent surfaces "Product X at Store Y is below its reorder threshold."
  • The LowInventoryActivator turns that into action: on_hand < reorder_threshold → alert the store manager.
Close: Same OneLake data, one semantic model, one ontology — powering a report, a conversational agent, and an automated alert. That's Fabric IQ.
Presenter tip: just before the demo, lower one on_hand value below its threshold so the Activator fires live during Act 4.

Deployment Guide (step by step)

Follow these to deploy the full demo into your own Fabric workspace. The deployment runs independently against the Fabric REST API — no MCP runtime needed.

Prerequisites: a Fabric-enabled workspace on an active capacity · contributor/admin rights · Python 3.10+ · the Az PowerShell module (for Connect-AzAccount). For the AI-assisted authoring experience you'll also set up VS Code + GitHub Copilot + the Fabric Core MCP Server (next section).

Set up your AI authoring environment (VS Code + Copilot + Fabric MCP)

This demo was built code-first with the Fabric Core MCP server guiding the work — it discovers item schemas, validates definitions, and derives the correct creation order. Set the same environment up so you (and Copilot) get accurate Fabric guidance while you build.

Install Visual Studio Code

Download and install VS Code (Stable or Insiders). On Windows, also install Node.js 20 LTS+ and Python 3.10+ if you don't have them.

Add GitHub Copilot

Install the GitHub Copilot and GitHub Copilot Chat extensions from the VS Code Marketplace and sign in with a GitHub account that has a Copilot license. Open the Chat view and confirm it responds.

Add the Fabric Core MCP Server (remote HTTP)

The Core server is a hosted endpoint — no local install. In VS Code:
  • Press Ctrl+Shift+P → MCP: Add Server → choose HTTP.
  • URL: https://api.fabric.microsoft.com/v1/mcp/core
  • Name it fabric. VS Code opens a browser to sign in with your Microsoft Entra ID; the window closes when done.
Or add it manually to .vscode/mcp.json: 
{
  "servers": {
    "fabric": {
      "type": "http",
      "url": "https://api.fabric.microsoft.com/v1/mcp/core"
    }
  }
}

(Alternative) Local Fabric MCP Server via npx

Prefer a local server / a non-Copilot MCP client? With Node.js 20 LTS+ installed, add to your client's mcp.json: 
{
  "mcpServers": {
    "fabric-mcp-server": {
      "command": "npx",
      "args": ["-y","@microsoft/fabric-mcp@latest","server","start","--mode","all"]
    }
  }
}
Or install the Fabric MCP Server VS Code extension, which registers it automatically.

Verify the MCP connection

In Copilot Chat, switch to Agent mode and confirm the fabric tools are listed (e.g. discover item schemas / list workspaces). Now Copilot can ground its Fabric code in live schemas.
MCP is an authoring aid, not the runtime. The MCP server helps you and Copilot generate correct payloads and ordering. The actual deployment below runs independently against the Fabric REST API — so the demo still deploys even on machines without MCP.

Get the demo — pick a path

Two ways to get the project onto your machine: (A) fork the ready-made repo, or (B) "vibe-code" it from scratch with Copilot + the Fabric MCP server. Both end at the same Deploy the demo steps below.

Path A · Fork & clone the repo fastest

  1. Open the source repo and click Fork (top-right) → creates a copy under your account/org:
    github.com/soocodes/fabric-mcp-core-demo
  2. Clone your fork (swap <your-username>) and install dependencies:
git clone https://github.com/<your-username>/fabric-mcp-core-demo.git
cd fabric-mcp-core-demo
pip install -r deploy/requirements.txt

# (optional) track the original repo to pull future updates
git remote add upstream https://github.com/soocodes/fabric-mcp-core-demo.git

Forking keeps your changes (workspace IDs, data tweaks) in your own repo and makes it easy to pull upstream updates later.

Path B · Vibe-code it with Copilot + MCP build from scratch

No repo needed — let Copilot Agent generate it, grounded by the Fabric MCP server you connected above.

Deploy the demo

Confirm the project & dependencies are in place

You should have the project folder locally (from Path A or B) with dependencies installed: 
cd fabric-mcp-core-demo
pip install -r deploy/requirements.txt

Set your target workspace

Edit config/deploy.config.json and set your workspaceId (and optionally adjust data volumes: stores, products, customers, orders).

Authenticate to Fabric

Connect-AzAccount
Interactive sign-in. (For CI, use a service principal + a FABRIC_TOKEN env var.)

(Optional) preview the synthetic data locally

python data/generate_data.py

Deploy everything (ordered, dependency-aware)

python deploy/deploy.py
Creates the Lakehouse, runs the load notebook, builds the Direct-Lake-on-SQL semantic model, the report, the Eventhouse, the data-bound Ontology, and the Activator. Item IDs are written to deploy_output.json.

Or deploy phases selectively

python deploy/deploy.py --only lakehouse,data,semantic,report
python deploy/deploy.py --only eventhouse
python deploy/deploy.py --only activator,preview
python deploy/deploy.py --skip eventhouse

Verify in the Fabric portal

Open your workspace — you should see RetailLakehouse, RetailSalesModel, RetailDemoReport (with data), RetailEventhouse, RetailOntology (5 entities), and LowInventoryActivator.
Why Direct Lake on SQL? Direct Lake on OneLake needs a bound OneLake credential and renders blank when created headless. This demo uses Direct Lake on the SQL endpoint (SSO), which deploys reliably and is verified returning $106,412.12 / 350 orders.

Finish & Run the Demo

After deploy.py completes, finish these preview/UI-only items (~15–20 min). They have no headless API, so they're done once in the portal.

Seed the Eventhouse data required for Act 4

Open RetailEvents KQL database → New queryset → paste & run eventhouse/setup.kql. This creates & seeds the InventoryEvents table.

Create the Activator alert — on the Eventhouse query required for Act 4

There is no Eventstream in this demo, so bind the alert directly to the KQL query: 
InventoryEvents
| where event_type in ('LowStock','StockOut')
| where on_hand < threshold
In the queryset ribbon click Set alert → check every few minutes → condition: when the query returns rows → action: email / Teams. This creates (or reuses) the LowInventoryActivator Reflex.

Create the Data Agent required for Act 3

New Fabric notebook → paste agents/data_agent_setup.py (preview fabric-data-agent SDK) → run. Point it at RetailSalesModel + RetailOntology, then test: "Which store has the highest revenue?"

Configure the Operations Agent optional

Apply the monitoring rules from agents/operations_agent_config.yaml in-product.

Pre-demo prep makes the alert fire live

Just before presenting, lower one on_hand value below its reorder_threshold so the Activator fires during Act 4.
Why these are manual: the KQL data-plane token isn't available headless, the Reflex rule schema isn't stable for headless authoring, and the Data/Operations Agents are preview with no public REST CRUD yet.
Suggested order: 1 → 2 → 3 → 4 → 5. Steps 1–3 are the must-haves for a full end-to-end run; 4–5 are polish.
